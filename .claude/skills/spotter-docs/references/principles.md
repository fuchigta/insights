# spotter の約束

spotter が利用者に対して守ることを並べたページです。ここに書いたことは spotter の
振る舞いの前提で、変える場合は破壊的変更として扱います。仕組みの詳しい説明は各項目の
リンク先にあります。

spotter はエージェントの代わりに考えるのではなく、「直さずに黙らせる」「片方だけ直す」
「申告と実態がずれる」といった失敗を機械的に捕まえることに徹します。以下はそのための約束です。

## 1. 手元で通ったものは CI でも通る

最も重要な約束です。

- `commit-msg` フック（`--message`）、`pre-push` フック（`--pre-push`）、CI（`--range`）
  から、同じ検査を同じ設定で呼べます（[hooks.md](hooks.md)、
  [ci-integration.md](ci-integration.md)）
- 免除はコミットメッセージのトレーラだけで表します。環境変数による免除は用意しません。
  手元でだけ効いて CI に届かない判断を作らないためです（[exemptions.md](exemptions.md)）
- `required_version` で、古いバイナリが新しい検査を走らせないまま通してしまうことを
  防げます（[versioning.md](versioning.md)）
- マージコミットは手元でも CI でも検査しません。取り込まれる側の各コミットは、
  マージされる前にそれぞれ検査済みという前提です（[hooks.md](hooks.md)、
  [ci-integration.md](ci-integration.md)）
- 同様に、`git commit --amend` で作り直すコミットの per-commit 粒度の検査
  （`diff-size`・`commit-intent`・amend で消えるトレーラの免除など）は、commit-msg の
  時点では amend かどうかを知る手段が git に無いため確定させられません。squashed
  粒度の検査（`doc-sync` など）は比較元を未 push 範囲の起点にすることでこの限界を
  避けますが（[granularity.md](granularity.md)）、per-commit 粒度は `pre-push` フックが
  push する前に CI と同じ range 検査を走らせることで確定します（[hooks.md](hooks.md)）
- 例外として、`--range` は範囲内の全コミットを実行時（HEAD・作業ツリー）の
  `.spotter.yml` で検査します。そのため範囲の途中で検査を足すコミットがあると、
  それより前のコミット（コミットした時点のフックは通っていた）が CI でだけ
  落ちることがあります。設定を途中で緩めて違反を混ぜ、後で戻すことで検査や
  免除を迂回できてしまわないようにするための割り切りです
  （[ci-integration.md](ci-integration.md)）。`pre-push` フックは push しようとしている
  範囲を実行時の設定で同じように検査するため、push する前にこのずれに気づけます
  （[hooks.md](hooks.md)）
- この割り切りでは、`.spotter.yml` を緩めたまま残す変更は、緩めた設定で検査されて
  通ってしまいます。これを捕まえる [`config-guard`](checks/config-guard.md)（オプトイン）
  だけは、実行時の設定から消されていても、範囲の比較元か終点の `.spotter.yml` に
  あれば走り、自身の免除設定を比較元の `.spotter.yml` から読みます。同じ変更で
  検査ごと消したり免除を有効にしたりして通すことを防ぐためです（導入していない
  利用者の挙動は変わりません）

## 2. 同じ入力なら同じ結果になる

検査の結果は、git の履歴・作業ツリー・コミットメッセージ・`.spotter.yml` だけで
決まります。組み込み検査はネットワークにも LLM にも依存せず、オフラインで動きます。

## 3. 結果は合格か不合格かの二値

警告のような中間の段階はありません。無視できる警告は、やがて無視されるからです。
`spotter check` は 1 つの検査が失敗しても残りを全部走らせ、結果をまとめて報告します。

## 4. 「後から直せば通るか」は検査ごとに決まっている

履歴に残ると困るもの（シークレットの混入など）は後から消しても通らず、後続の
コミットで補えるもの（ドキュメントの更新など）は補えば通ります。この区別は検査の
意味そのものなので、検査ごとに固定で、設定からは変えられません
（[granularity.md](granularity.md)）。

## 5. 免除には理由が要る

免除トレーラは理由を書かない限り効きません。例外にした判断は、理由と一緒に git の
履歴に残ります。`commit-subject` はメッセージの体裁そのものを
検証するので、免除トレーラを書き足すだけで回避できてしまわないよう、既定で免除できません（[exemptions.md](exemptions.md)）。
免除トレーラはメッセージ本文の最後の段落（トレーラ段落）に書く必要があり、検査によっては
対象を検査の一部に絞れます（[exemptions.md](exemptions.md)）。

## 6. 特定の言語やプロジェクトを前提にしない

テストファイルの命名のような言語ごとの知識は、既定値として持ちません。設定例は
「レシピ」としてドキュメントに置き、何を検査するかは利用者が `.spotter.yml` で決めます。
組み込みに寄せられない固有の検査は、外部コマンドとして同じ仕組みに載せられます
（[checks/command.md](checks/command.md)）。

## 7. 設定の誤りを黙って無視しない

知らない type やオプション、型の合わない値は、検査を走らせる前にエラーにします。
「書いたつもりの検査が実は効いていなかった」を作らないためです。効いていない
パターンなど、陳腐化した設定は `spotter config lint` で見つけられます
（[config-reference.md](config-reference.md)）。

## 8. 利用者の環境を壊さない

- 既存のフック設定（`core.hooksPath` や他のフックランナー）を尊重し、共存します
  （[hooks.md](hooks.md)）
- `hooks install` や `skills install` は何度実行しても同じ結果になります
- spotter が置いたものだけを書き換え・削除し、それ以外は明示的な指示（`--force`）が
  無い限り触りません（[skills.md](skills.md)）
- `update` はダウンロードしたバイナリのチェックサムを検証してから置き換えます
  （[update.md](update.md)）

## 9. 機械も読める

人間向けの表示とは別に、組み込み検査の一覧や設定の診断結果を JSON で出力できます
（`spotter checks --json`、`spotter config lint --json`）。コーディングエージェントが
ドキュメントの散文ではなく実装から生成された情報で判断できるようにするためです。
