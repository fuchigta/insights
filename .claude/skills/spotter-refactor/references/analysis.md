# 免除頻度・ノイズ量の測り方

`spotter-refactor` の手順3・4の具体的なコマンド例です。

## 免除トレーラの濫用頻度を測る

免除トレーラは `<トレーラ名>: skip <理由>`（大文字小文字を区別しない）、または対象を
絞る `<トレーラ名>: skip[<対象>,...] <理由>` という形式です（本来はコミットメッセージ
本文の最後の段落だけが対象ですが、この集計は簡易的に本文全体から数えます。同梱されて
いれば `spotter-docs` スキルの `exemptions.md` に仕組みの詳細があります）。
直近のコミットメッセージから、トレーラ名ごとの出現回数を数えます。

```bash
git log --format=%B -200 | grep -ioE '^[a-z][a-z0-9-]*:[[:space:]]*skip(\[[^]]*\])?[[:space:]]' | tr 'A-Z' 'a-z' | sort | uniq -c | sort -rn
```

`skip(\[[^]]*\])?` は角括弧付きのスコープ付き免除（`skip[docs/a.md]`）も 1 件として数える
ためです。角括弧が無い従来の `skip <理由>` にもそのまま一致します。

`tr` で小文字化してから集計しているのは、同じトレーラでも打ち間違いで大文字小文字が
揺れていると別行に分かれてしまうのを防ぐためです（例: `Doc-Sync: skip` と
`doc-sync: skip` が別集計になる）。

出力例:

```
  8 diff-content: skip
  3 doc-sync: skip
  1 commit-intent: skip
```

**この数字だけでは判断できません。** 同じ検査でも「毎回違う正当な理由で免除されている」
のか「実質的に同じ理由を毎回書かされている」のかで意味が違います。頻度が高い検査は、
実際の免除理由（`git log --format=%B -50 --grep='^Diff-Content: skip'` のように絞り込んで
本文を読む）を確認してください。同じような理由が繰り返し出てくるなら、それは
`.spotter.yml` 側の対象・除外パターンで先回りして潰せるはずのパターンです。

`-200` は目安です。リポジトリのコミット頻度に応じて調整してください（コミット数が
少ないリポジトリでは全履歴でも構いません）。

トレーラ名は既定でキー名（`checks.<key>`）から自動生成されますが、
`checks.<key>.exempt.trailer` で明示的に上書きされている場合があります。集計した
トレーラ名がどの検査キーに対応するかは `.spotter.yml` の `exempt.trailer` も
確認してください（`spotter doctor` の出力にはトレーラ名は出ません）。

## 検査のノイズ量を測る

過去のコミットに対して実際に検査を走らせ、**免除されなかった失敗**が何回起きたかを
数えます（免除が成立したコミットは「免除されました」という別の行になり、この集計には
現れません。「免除頻度は高いのにノイズ量が低い」検査は、むしろ「ほぼ免除で回避されて
いる」ことの兆候です。詳しくは下の判断軸を参照）。

```bash
spotter check --range "-10 HEAD" 2>&1 | grep -oE '^[^ ]+ の検査に失敗しました' | sort | uniq -c | sort -rn
```

`-10 HEAD` はリポジトリのコミット数に合わせて調整してください（例: 直近 5 コミットなら
`-5 HEAD`）。コミットが足りなければ最初のコミットまで全部が対象になるため、短い履歴の
リポジトリでも失敗しません。

grep パターンは `[^ ]+`（スペース以外の1文字以上）にしています。検査のキー名は
`checks.<key>` で自由に付けられ、大文字やアンダースコアを含むこともあるため、
`[a-z][a-z0-9-]*` のような文字種を絞ったパターンだと該当リポジトリの命名によっては
検査結果を取りこぼします。

`worktree` 粒度の検査（`doc-paths`/`consistency`/`doc-links`）は `--range` の値に
関わらず現在の作業ツリーを1回だけ見るため、この方法では「今落ちているか」の
0/1 しか分かりません。頻度ではなく `spotter config lint` の検出結果と併せて
判断してください。抽出結果そのものを見たいときは `spotter config explain <検査名>` が
使えます（`spotter checks --json` の `explain_supported` が true の type だけ）。

### 免除頻度とノイズ量を組み合わせた判断軸

| 免除頻度 | ノイズ量（免除されなかった失敗） | 意味 |
|---|---|---|
| 低い | 高い | 検査に引っかかるたびに実際にコードやコミットメッセージを直して通している。**検査が機能している証拠なので触る必要はありません** |
| 高い | 低い | ほとんどのケースが免除で通過している。**検査の対象・基準が実態と合っていない兆候です** |
| 高い | 高い | 免除でも通せず失敗もしている。基準が厳しすぎるか、免除理由が実際の違反内容と噛み合っていない可能性があります |
| 低い | 低い | 特に問題なし |

## 変更案の根拠をまとめる例

手順6で利用者に提示する際は、検査ごとに次の形でまとめると判断しやすくなります。

```
- diff-content: 直近10コミット中、免除トレーラ 8 回・免除されなかった失敗 0 回
  → 免除理由は全て「外部ライブラリの型定義が壊れている」
  → 該当パターン（@ts-ignore の deny）に paths で対象を絞れば解決しそう
  → 提案: deny[].paths を 'src/**/*.ts' に限定する（修正）

- doc-sync-legacy: spotter config lint で pairs[0].paths が現在の作業ツリーに
  一致しないと報告された
  → 対応するディレクトリが internal/legacy/ から internal/core/ にリネーム済み
  → 提案: pairs[0].paths を internal/core/*.go に更新する（修正）

- consistency-old-versions: spotter config lint で sources[1].file が存在しない
  と報告された。対応するファイル自体が削除されている
  → 提案: このチェック全体を削除する（削除）
```
