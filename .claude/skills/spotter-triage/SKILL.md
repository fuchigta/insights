# spotter の検査に落ちたときの対処

spotter の検査が失敗したら、次の3択のどれかで対処します。**この順番で検討してください**
（下に行くほど最終手段です）。`git commit --no-verify` でフックをすり抜けるのは選択肢では
ありません。「直さずに黙らせる」失敗を捕まえるためにある検査を、まさにその方法で回避する
ことになります。

1. **違反そのものを直す** — 最優先。多くの検査はコーディングエージェントの「直さずに
   黙らせる」失敗を捕まえるためにあるので、まず違反箇所を直すのが正しい対処です。
2. **`.spotter.yml` の設定を直す** — 検査の対象・除外パターンがリポジトリの実情と
   ズレている（新しいディレクトリを追加したのに `path_prefixes` に無い、生成ファイルが
   `exclude` に無い等）場合。1個所の小さな修正ならその場で直して構いませんが、複数の
   検査で食い違いが目立つ、または `.spotter.yml` 全体を見直したい規模なら、設定の
   陳腐化を体系的に洗い出すスキルに委ねてください（`spotter skills list` で同梱されて
   いるか確認できます。無ければ利用者に相談してください）。
3. **免除トレーラで例外扱いする** — 違反ではなく意図した変更だと確信できる場合だけ。
   理由を書かせる仕組みなので、雑な理由（「必要だから」等）で書かない。同じ検査に何度も
   免除を書くことになったら、それは 1 や 2 が必要なサインです。

## commit-msg フックで弾かれた場合は「後で直す」が使えないことがある

以下の表の「典型的な直し方」で「後続コミットで解消できる」と書いている検査
（squashed 粒度: `doc-sync` / `companion-files`）は、**`--range`（CI）で落ちた場合の話**
です。`commit-msg` フックはステージ済みの変更を 1 回だけ見るため、その場でコミットが
拒否されます。後から別コミットで直す選択肢はなく、**今コミットしようとしている変更に
含めて直す**必要があります。

## pre-push フックで弾かれた場合は履歴を直しても push 前なら安全

pre-push フックは range モードで、まだどのリモート追跡ブランチにも取り込まれていない
ローカルのコミットだけを検査します（詳しくは同梱されていれば `spotter-docs` スキルの
`hooks.md` を参照）。**この範囲は定義上まだ push していない**ので、`git commit --amend`
や `git rebase -i` で直しても force push の心配はありません。squashed 粒度の検査
（`doc-sync` / `companion-files`）は、その push に含めた範囲のどれか1コミットで
直せば十分です。

出力される「検査した ref とその範囲式」「`.spotter.yml` を変更したコミットの一覧」は、
どのコミットで検査が増えたかを特定する手がかりです。`--no-verify` で pre-push をすり
抜けても、最終的には CI（`--range`）が同じ範囲を検査するため、push 前に気づけなかった
だけで結果は変わりません。

## 検査 type ごとの典型的な直し方

| type | 落ちたらまず疑うこと | 典型的な直し方 | 免除 |
|---|---|---|---|
| `doc-sync` | コードは直したがドキュメントを直し忘れた | 対応する `doc` を更新する。CI（range）で落ちた場合は後続コミットでも解消できるが、フックで弾かれた場合は今のコミットに含める | 有効（既定） |
| `unwanted-files` | ログ・シークレット・ビルド成果物などが混入した | 該当ファイルを削除し、必要なら `.gitignore` に追加する。**per-commit 粒度なので後から消しても履歴には残る**。シークレットが混入していた場合は、削除するだけでなく**そのクレデンシャルのローテーションを利用者に促す**こと（履歴書き換えの安全性については下記の注記を参照） | 有効（既定） |
| `doc-paths` | ドキュメントが名指ししているコードパスをリネーム・削除した | ドキュメント側の記述をリネーム後のパスに合わせる。誤検知（実際は問題ない言及）なら `ignore` に追加する | **無し**（worktree 粒度） |
| `commit-subject` | コミットメッセージの1行目が Conventional Commits の形になっていない | メッセージを書き直す（履歴書き換えの安全性については下記の注記を参照） | **既定で無効**（体裁の検証を免除で回避すると矛盾するため） |
| `consistency`（type=consistency） | 複数ファイルに同じ情報を手で転記していて片方だけ更新した | 食い違っている側を直す。どちらが正か分からなければ両方のファイルを見て判断する。`ignore` のような除外オプションは無いので、`sources[].extract` の正規表現がファイルの記法変更に追従できていない（抽出0件でエラーになる）ことも疑う | **無し**（worktree 粒度） |
| `diff-content` | 抑制コメント・コンフリクトマーカー・テストの skip/削除などが追加行（または削除行）に混入した | 抑制せず根本原因を直す。**「直さずに黙らせる」を検知する検査なので、免除は慎重に**。正当な理由（外部 API の型定義が壊れている等）があるときだけ理由を明記して免除する | 有効（既定） |
| `commit-intent` | 申告した commit type/scope と実際の差分の内容が噛み合わない（`docs:` なのにコードを触っている等） | メッセージの type を実態に合わせるか、差分を type の主張に合わせて絞る（別コミットに分ける）。テスト不要な軽微な変更等、正当な理由があれば免除して良い | 有効（既定） |
| `companion-files` | 触ったファイルに必要な相方（テスト、型定義、down マイグレーション等）が無い | 相方ファイルを作成する。CI（range）で落ちた場合は後続コミットでも解消できるが、フックで弾かれた場合は今のコミットに含める | 有効（既定） |
| `doc-links` | Markdown のリンク（`[text](target)`）が指すファイルが存在しない | リンク先を直す。意図的に壊れたローカルパスを残したい場合だけ `ignore` に追加する（`http(s)://`・`mailto:` などスキーム付きの外部 URL はそもそも検証対象外なので `ignore` は不要） | **無し**（worktree 粒度） |
| `diff-size` | 1コミットの変更量（ファイル数・行数）が上限を超えている | 目的の異なる変更が混ざっていないか確認し、コミットを分割する。一括リネームやフォーマッタ適用など、意図した大きな変更なら理由を明記して免除する | 有効（既定） |
| `command`（command 型） | 上記に無い、リポジトリ固有の検査 | 検査ごとの出力メッセージをまず読む（固有ロジックなので一般的な直し方は無い）。設定は `types.<type>.command`/`args`（何を実行しているか）と `default.granularity` を確認する | 有効（既定）。ただし `default.granularity: worktree` なら仕組み自体が無い |

`type` はキー名ではなく `.spotter.yml` の `checks.<key>.type` の値です。落ちた検査のキー名
から type が分からない場合は `spotter doctor` で一覧を確認してください。

## 免除トレーラを使うときの注意

```
<トレーラ名>: skip <理由>
```

- トレーラ名は既定でキー名から生成されます（`doc-sync` というキーなら `Doc-Sync`）。
  `.spotter.yml` の `checks.<key>.exempt.trailer` で明示的に上書きされていないか確認
  してください（`spotter doctor` の出力にはトレーラ名は出ません）。
- 理由は必須です。空の免除は拒否されます。
- **トレーラはコミットメッセージ本文の最後の段落（空行で区切った最後のブロック）に
  書いてください。** 本文の途中に `<トレーラ名>: skip` で始まる説明文を書いても免除には
  なりません（git のトレーラと同じ扱いです）。
- 一部の検査（`doc-sync` など）は `<トレーラ名>: skip[<対象>,...] <理由>` の形で、免除の
  対象を検査の一部に絞れます。対応している検査と対象の単位は `spotter checks --json` の
  `exempt_scoped_supported` / `exempt_scoped_target_kind` で確認できます。
- **per-commit 粒度**（`unwanted-files` / `commit-subject` / `diff-content` /
  `commit-intent` / `diff-size`）は、免除トレーラを**違反したそのコミット自身**の
  メッセージに書く必要があります。後から別のコミットに免除トレーラを書いても、
  過去のコミットは免除されません（範囲内のコミットごとに個別に見る粒度のため）。
- **squashed 粒度**（`doc-sync` / `companion-files`）は、範囲内のどれか1コミットに
  書けば効きます。
- **worktree 粒度**（`doc-paths` / `consistency` / `doc-links`）は免除トレーラの
  仕組み自体がありません。誤検知は検査ごとの `ignore` 等の設定で個別に潰してください。

### 過去のコミットのメッセージを直す必要があるとき

`unwanted-files` や `commit-subject` のように per-commit 粒度の検査で、既にコミット
してしまった過去のコミット（直前のコミットなら `git commit --amend`、それより前なら
`git rebase -i`）を直す場合は、そのコミットが**既に push 済みかどうかを確認して
ください**。push 済みのブランチを書き換えると force-push が必要になり、共有ブランチの
場合は他の人の作業に影響します。**push 済みの履歴を書き換える前は、必ず利用者に
確認してください。**

## 迷ったら

`.spotter.yml` の書き方や検査 type の詳しい仕様を確認したいときは、同梱されていれば
`spotter-docs` スキル（`spotter skills list` で確認できます）の `references/` を
参照してください。`.spotter.yml` を書き換えたら、提示・コミットする前に必ず次の
どちらかで検証してください。

```bash
spotter doctor --config .spotter.yml
spotter check --config .spotter.yml --range "-10 HEAD"
```

`consistency` / `doc-paths` / `doc-links` が「何も抽出できなかった」「想定と違う要素を
拾っている」ことで落ちているときは、正規表現や設定を推測で直す前に
`spotter config explain <検査名>` で、実際に何をどの行から抽出しているかを確認して
ください（合否は出ません。合否は `spotter check <検査名>` で確かめます）。
