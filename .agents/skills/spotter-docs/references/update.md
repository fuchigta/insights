# バイナリの更新（`spotter update`）

```
spotter update [--check] [--version <バージョン>]
```

`spotter` 自身を GitHub Releases の配布バイナリで置き換えます。手元の環境に
Go は要りません（[インストール](../README.md#インストール)と同じ配布物を使います）。

## 挙動

1. 実行中の OS/アーキテクチャから、対応する配布アセット名
   （`spotter-<goos>-<goarch>[.exe]`）を組み立てます。
   `.github/workflows/release.yml` のビルドマトリクスに無い組み合わせ
   （例: `windows/arm64`）はエラーにします。
2. `--version` を指定しなければ、GitHub の `/releases/latest` へのリダイレクト先
   から最新タグ名を取得します（GitHub API は使いません。認証無しだとレート制限
   （60 req/h）にすぐ達するため、リダイレクト先の URL だけを見ます）。
3. 手元のバージョンと比較し、既に対象バージョン以上なら何もせず終了します
   （`--version` 指定時は比較せず常に取得し直します。特定バージョンへの固定・
   巻き戻しのために使う想定のためです）。
4. アセット本体と、同じ URL に `.sha256` を付けたチェックサムファイルを取得し、
   SHA-256 が一致することを確認してから、実行中のバイナリをその内容で
   置き換えます。

置き換えは、同じディレクトリに書いた一時ファイルへの 2 段階の rename
（旧バイナリを `.old` へ退避 → 新バイナリを配置）で行います。rename は実行中の
ファイルに対しても許される操作（Unix はそもそも問題無く、Windows も実行イメージは
delete 共有付きで開かれているため rename/delete できます）なので、実行中の
`spotter update` プロセス自身の実行を止めずに済みます。退避した `.old` の削除は
ベストエフォートです（削除できなくても動作に影響は無く、次回の `update` 実行時に
上書きされます）。

## `--check`: 確認だけ行う

```
spotter update --check
```

実際には更新せず、現在のバージョンと最新バージョン、更新の要否だけを表示します。

## `--version`: 特定バージョンに切り替える

```
spotter update --version v1.2.3
```

指定したタグのバイナリを取得します（`v` は省略可）。ロールバックや、
`required_version` に合わせてピン留めしたい場合に使います。

## dev ビルドの扱い

このリポジトリ自身のソースを `go run ./cmd/spotter` で実行した場合、
バージョンは `dev` になり正式なバージョン文字列として比較できません
（[versioning.md](versioning.md) 参照）。この場合 `spotter update` は
「既に最新」の判定ができないため、常にリリースバイナリの取得・置き換えを
実行します。`go run` でソースを直接使っている環境（このリポジトリ自身の
commit-msg フックがそうです。[hooks.md](hooks.md) 参照）では、置き換え対象が
使い捨ての一時バイナリになるため実質的に意味を持ちません。

なお `go install .../spotter@latest` のようにモジュールとして取得した場合は、
`go install` した時点のタグ相当のバージョンが取れるため `dev` にはなりません
（[versioning.md](versioning.md) 参照）。
