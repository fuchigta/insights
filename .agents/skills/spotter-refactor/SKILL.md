# .spotter.yml の体系的な見直し

`.spotter.yml` を持つリポジトリで、その設定がリポジトリの現状と噛み合わなくなって
いないかを見直す手順です。1個所だけの小さな修正（検査に落ちてその場で `.spotter.yml`
を直す）は、同梱されていれば `spotter-triage` スキルの範囲です。このスキルは
「複数の検査で食い違いが目立つ」「`.spotter.yml` 全体を棚卸ししたい」という、
もっと大きな規模の見直しが対象です。

## 前提確認

`.spotter.yml` が無いリポジトリはこのスキルの対象外です（新規セットアップは、
同梱されていれば `spotter-setup` スキルの範囲）。`spotter --version` を確認し、
`spotter checks --json` で組み込み検査の正しい設定キーを取得してください（このスキルの
散文より優先する）。

## 手順

1. **現状把握** — `spotter doctor` で設定済みの検査一覧・フック設置状況を確認する
2. **死んだ設定の機械的な検出** — `spotter config lint`（`--json` も使える）を実行する。
   出力される検出結果は「現在の作業ツリーと一致しなくなったパターン」「実在しない
   ファイル参照」「どの `checks` からも使われていない `types`」です。**これは削除・
   修正の一次候補です。** 手で目視するより先に必ず実行してください
3. **免除トレーラの濫用頻度を測る** — 特定の検査に免除が頻発しているなら、それは
   「検査が実態に合っていない」最有力候補です。具体的なコマンドは
   `references/analysis.md` を参照してください
4. **検査のノイズ量を測る** — 過去のコミット・現在の作業ツリーに対して実際に
   検査を走らせ、どの検査が何回落ちるかを数える。具体的なコマンドは
   `references/analysis.md` を参照してください
5. **カバレッジの穴を探す** — リポジトリに新しく増えたトップレベルディレクトリや
   言語（新しいマニフェストファイルの追加など）が、既存の `checks` でカバーされて
   いるか確認する。検出の具体的な手がかりは、同梱されていれば `spotter-setup`
   スキルの `detection.md` を参照してください（新規セットアップと同じ観点で
   「何を見て何を判断するか」が使えます）
6. **変更案を3分類でまとめる** — 手順2〜5の結果を「削除」「修正」「追加」に分類し、
   それぞれの根拠（`config lint` の検出結果、免除の頻度、ノイズの多さ、カバレッジの
   穴）を添えて利用者に提示する。**利用者の承認を得てから `.spotter.yml` を
   書き換えてください。** 特に「削除」は検査そのものを弱める変更なので、機械的な
   検出結果があっても独断で消さない
7. **再検証** — 変更後、`spotter doctor` と `spotter check --range <直近の範囲>` で
   もう一度確認する。理想は、変更前より違反件数・免除の必要性が減っていることです

## 判断の指針

- `spotter config lint` が検出結果を出したフィールドは、多くの場合「削除」か
  「パスの更新」で解決します。ただし `doc-sync.pairs` のようにコード側の
  リネームに追随できていないだけの場合は、パスを直すだけで検査の価値は戻ります。
  安易に丸ごと削除しないでください
- `consistency` の `extract` / `line` / `until` を見直すときは、`spotter config explain <検査名>`
  で抽出結果（ブロックの行範囲、拾った要素と出現位置）を確認してから直してください。
  `subset` の source が想定より少なくても通ってしまっていないかも、ここで分かります
- 免除が頻発していても、検査自体を消すのが正解とは限りません。設定側の対象・
  除外パターンを調整するだけで直る場合が多いです（同梱されていれば `spotter-setup`
  スキルの `rollout.md` にある「対象を絞る→除外を足す→パターンを緩める→一旦外す」
  という優先順位は、新規導入だけでなく見直しにもそのまま使えます）
- `commit-subject`/`commit-intent` のように**体裁・意図の検証をする検査**は、
  免除頻発の理由が「チームの合意が変わった」ことにある場合があります。その場合は
  検査の設定ではなく、チームへの確認が先です
- worktree 粒度の検査（`doc-paths`/`consistency`/`doc-links`）は免除の頻度を
  測れません（免除トレーラの仕組み自体が無いため）。これらは `spotter config lint`
  の検出結果とノイズ量（`spotter check` の直近の失敗回数）だけで判断してください

## 仕上げの前に

`.spotter.yml` を書き換えたら、提示・コミットする前に必ず手順7（再検証）を
やり直してください。
